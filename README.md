# Ferrite

Ferrite is a Rust agentic browser, built on the [Servo](https://servo.org/)
engine, that defends AI browser agents against **indirect prompt injection
(IPI)** architecturally rather than by trying to detect malicious text.

## The idea

An AI agent browsing the web reads content it doesn't control. Some of that
content can carry instructions aimed at the agent, not the user — a hidden
`<div>`, an HTML comment, an image `alt` attribute, a field in a tool's JSON
response. Ferrite doesn't try to win the arms race of spotting every phrasing
of an injected instruction. Instead it watches *what the agent does*:

1. **Predict** the task's expected fingerprint — which tools and origins the
   task legitimately needs — from the user's prompt, before any untrusted
   content is read.
2. **Dry-run** the agent's actual plan in a sandbox against synthetic,
   fake-but-plausible data, with no real network reachable.
3. **Compare** what the agent actually did against what was predicted.
4. **Consent-gate** anything beyond the prediction in a trusted UI surface,
   decoupled from page content, before the real run proceeds.

A successful injection can still make the agent *try* something unexpected —
but trying it during a contained dry-run against fake data, gated behind a
consent prompt the user controls, is a very different outcome than trying it
for real. The real run is held to the same prediction: an action outside it
pauses and asks. A SHA-256 hash-chained audit log records the security-relevant
events so containment is verifiable after the fact, not just asserted.

## Status

As of 2026-10-04. The A0–A13 rebuild plan (`docs/REBUILD_DIRECTIVE.md`) is
**complete**: every charter ran, every defect in the D1–D14 register was fixed
or explicitly ratified as intended behavior, and `docs/EVALUATION.md` reports
real numbers from a real corpus with no fabricated data anywhere.

**It does not mean "feature-complete" or "ready to trust in production."**
Read `docs/EVALUATION.md` §5, §6 and §8.6 before drawing any conclusion from the
eval numbers. In particular:

- **The app runs on the new stack.** `ferrite-ui`/`ferrite-shell` construct a
  real `ferrite-model` provider and drive `ferrite_agent::browser_loop` against
  the real Servo engine. A provider is connected from the app's Settings drawer
  (provider, API key in the OS keyring, models) or from the environment
  (`docs/DECISIONS.md` ADR-017). Only Ollama (cloud or local) and Gemini exist;
  there is no OpenAI-compatible or Anthropic backend (`docs/TO-DO.md` T-277).
- **The real run is gated too.** The predicted fingerprint is binding on the
  real run: an action outside it pauses and asks you (ADR-014, ADR-020).
- **The offline corpus is 938 cases** (`docs/EVALUATION.md` §8), of which 909 are
  generated by `scripts/gen_redteam_corpus.py`. The agent in it is scripted, the
  cases are self-authored and template-generated, and no second author exists, so
  the intervals understate the uncertainty (`docs/TO-DO.md` T-227). A further
  **1,046 AgentDojo cases** are imported (`docs/EVALUATION.md` §10).
- **No real model has been run through the evaluation yet.** The live runner
  (`live_eval`, `docs/EVALUATION.md` §9) is finished and tested against a mock
  provider and a loopback fake server; its first run against Gemini or Ollama
  Cloud is still to do (`docs/TO-DO.md` T-275, T-278).
- **Rendering.** Real web pages need the Servo build (`just setup-servo`); the
  default build has no web rendering. The engine is Servo 0.6.0 from crates.io
  plus one vendored one-function patch (`vendor/servo-script`, ADR-022). Pages
  use features Servo lacks (`:has()`, `@container`, `aspect-ratio` on blocks,
  ...), so some sites look wrong (`docs/TO-DO.md` T-264). The address bar
  searches Google; the agent's own search prompt still uses DuckDuckGo Lite.
  Since 2026-10-03 the engine is told the display scale, rendering uses a GPU
  context where it passes a start-up self-test (macOS by default) and otherwise
  the CPU, and thread pools follow the core count (ADR-021, T-280 to T-282).
- **Not verified on the owner's Mac or any real GPU** (as of the dated entries
  in `docs/PROGRESS.md`): the GPU path, the display-scale fix, the log file's
  location, quitting, DevTools, the page-control overlays and the resizable
  panels were checked on Linux (software rendering, Xvfb) only. The rolling
  `latest` release is built from `main`, which does not yet contain the
  2026-10-03 and 2026-10-04 work.
- **Known open problems:** GitHub does not open for the owner and the cause is
  unknown (T-290); Google sign-in (T-267) and the Google results margin (T-291)
  are unconfirmed; speed on real hardware is unmeasured (T-296); the Network tab
  has no status, size or timing (T-292); Windows writes no log file (T-298).
  `docs/TO-DO.md` has every open item with its commit and what was not verified.

`docs/PROGRESS.md` is the dated, cited status record; `docs/TO-DO.md` is the
live task ledger. Read those for current state, not this section, once time
has passed since it was written.

There is no `LICENSE` file yet; the crate manifests say `MIT OR Apache-2.0` and
the choice is waiting on the owner (`docs/TO-DO.md` T-209).

## Quick start

`just` is the command surface (`just --list` prints every recipe, and
`docs/COMMANDS.md` explains each). Plain `cargo` works too.

```
just setup-all                # real Servo build (20-60 min, 10+ GB first time) + local Laya, all inside this folder
$EDITOR .ferrite/env.local    # set FERRITE_MODEL_SMALL and FERRITE_MODEL_MAIN (or connect a model in the app's Settings instead)
export OLLAMA_API_KEY=...     # or store it in the keychain, or paste it into Settings
just run-all                  # real-Servo browser (dev profile) + the local Laya server
just run-fast                 # the same with the release profile: what to use to use it
```

| You want | Run |
|---|---|
| a checklist of what is ready on this machine | `just doctor` |
| the UI only, no web rendering, nothing to set up | `just run` |
| format, lint and unused-dependency gates | `just check` |
| the full test suite (no network, no API key) | `just test` |
| the offline evaluation | `just eval`, `just guard-eval` |
| a real model in the evaluation loop | `just live-eval-plan ...` then `just live-eval ...` |
| a crash or freeze report to send | `just collect-logs` |
| does this page work in Ferrite? | `just page-shot <url> 8000 /tmp/shot.png` |

Tools: `rustup` (stable, with `rustfmt`, `clippy`, `llvm-tools`; `rust-toolchain.toml`
pins these), and optionally `brew install just cargo-deny` (or
`cargo install just cargo-deny`) and `cargo install cargo-machete --locked`.
`just install-hooks` wires the commit-msg and pre-commit git hooks.

## Workspace

```
crates/
├── ferrite-core           types, IDs, capability/primitive taxonomy, OriginScope, Clock
├── ferrite-model          ModelProvider trait: Mock/Replay/Ollama/Gemini + cache/throttle/budget decorators, settings, keyring
├── ferrite-audit-log      SHA-256 hash-chained, SQLite-backed audit log
├── ferrite-ipi            the IPI defense: fingerprint, sanitizer, dry-run, twin, comparator
├── ferrite-engine         BrowserEngine trait + MockEngine (always built, no feature flag)
├── ferrite-engine-servo   ServoEngine and BorrowedServoEngine, BrowserEngine over real Servo (feature `engine-servo`)
├── ferrite-agent          the agent loop (browser_loop), chats, page context, the optional Laya decider
├── ferrite-servo          the live app's Servo integration (HeadlessServoSession, GPU context, diagnostics), feature `servo`
├── ferrite-ui             Iced UI: tabs, address bar, DevTools, agent panel, consent cards, settings
├── ferrite-shell          top-level binary, CLI dispatch, log file
└── ferrite-eval           evaluation harness (Servo-free): corpus, harness, adjudication, metrics, live model runner
vendor/
└── servo-script           servo-script 0.6.0 with one patch (not a workspace member; see FERRITE-PATCHES.md)
```

Two things that look like duplication and are not: `ferrite-servo` is the
integration the live app runs (`HeadlessServoSession`, one session per tab), and
`ferrite-engine-servo` adapts it to the engine-agnostic `BrowserEngine` trait;
the app uses `BorrowedServoEngine` (it borrows the tab's own session). The other
adapter, `ServoEngine`, owns its sessions and does not yet complete a real page
load in the headless harness (`docs/TO-DO.md` T-220). The target architecture in
`docs/REBUILD_DIRECTIVE.md` §4 also names a `ferrite-cli` crate; it was never
split out of `ferrite-shell`, which remains the one binary.

Servo (`ferrite-servo`'s `servo` feature, or `ferrite-engine-servo`'s
`engine-servo` feature) is not built by default: most development and all of the
IPI defense logic never touches it. See `CLAUDE.md` for the hard invariants and
for what was deliberately deleted and must not come back.

## Running locally

macOS first; Linux is best-effort; Windows has not been tried with the scripts.
Every step is idempotent. Everything lives inside this checkout: build output in
`target/` and all local state (Laya venv and checkpoint, `env.local`, profile,
settings) in the gitignored `.ferrite/` (override with `$CARGO_TARGET_DIR` /
`$FERRITE_HOME`); `rm -rf .ferrite` removes all local state. Without
`FERRITE_HOME` the app itself keeps its data in `~/.local/share/ferrite`.

```
just setup            # Servo-free build, optional Laya; add --dry-run --yes to see the plan
just setup-servo      # the real Servo engine: needed for real pages
just setup-all        # both, plus Laya
just doctor           # what is ready, what is not (--fix-hints says how to fix it)
just run-local        # reads .ferrite/env.local, starts Laya if set up, runs whichever build setup made last
just run-all          # force the Servo build
just run-fast         # Servo, release profile
```

`just setup` checks git, Xcode command line tools, Homebrew and the brew
packages CI installs (`cmake pkg-config openssl sqlite`), and rustup. It offers
to install what is missing but only after you say yes (or pass `--yes`), and it
never uses `sudo`. API keys are never written by these scripts: they come from
your environment, the OS keychain, or the Settings drawer. No model name is a
default, so `FERRITE_MODEL_SMALL` and `FERRITE_MODEL_MAIN` must be set in
`env.local` for `run-local` (`just models-local` lists the tags your endpoint
serves), or pass `--no-model-check` and connect a model in Settings. A key stored
with `security` may make macOS ask once whether `ferrite-shell` may read it; a
rebuilt binary can trigger that prompt again.

**Servo or not.** The default build is Servo-free: quick (about two minutes
cold, per `docs/BUILD_BUDGET.md`), but it has **no real web rendering**. For
real pages run `just setup-servo` (`cargo build -p ferrite-shell
--features ferrite-servo/servo`; audio and video playback are not built in, so no
extra brew package is needed): plan on 20 to 60 minutes and 10+ GB of disk the
first time. `just run-local` uses whichever build setup made last; force one with
`--servo` / `--no-servo`.

**Laya (optional).** [Laya](https://github.com/NandhaKishorM/laya) is a small
local decision model. Given the page state and the candidate elements it scores
"which operation, which element" for the next browser step. Ferrite talks to it
over HTTP only when `FERRITE_LAYA_URL` is set; with it unset the app runs exactly
as before, LLM only. `just setup` creates a Python venv under `$FERRITE_HOME/laya`,
installs `laya[serve]`, and downloads the `cklxx/laya-browser` checkpoint from
Hugging Face (`v10s`, the faster 322M one, by default; `--laya-checkpoint v10` for
the 421M one; skip all of it with `--no-laya`). `just run-local` then starts a
local server on `127.0.0.1:8765` for the session, waits for `/health`, sets
`FERRITE_LAYA_URL`, and stops the server when the app exits. Apple silicon uses
the Metal (`mps`) backend automatically; on the owner's Mac that was slower than
the LLM it was meant to beat (`docs/TO-DO.md` T-250), and the app stops asking
Laya by itself when it does not pay off (ADR-015). `just laya-verify` measures
yours. The server binds loopback only and refuses any other address unless an API
key is set.

Settings for the scripts live in `$FERRITE_HOME/env.local` (plain `KEY=VALUE`,
read as data, never sourced; only `FERRITE_*`, `OLLAMA_*`, `GEMINI_*` and
`RUST_LOG` are honoured; anything already exported in your shell wins).
`scripts/local.env.example` documents every knob. **A packaged app does not read
`env.local`**: connect a model from its Settings drawer.

## Using the browser

Tabs, an address bar (a URL, a bare host, or a search: anything else goes to
Google), back/forward/reload, an **Agent** toggle, an **Audit** shield, and one
overflow menu (zoom, find, bookmarks, history, downloads, developer tools, theme,
settings). A few shortcuts (Cmd on macOS, Ctrl elsewhere; the full table is in
`docs/COMMANDS.md`): `T` new tab, `W` close, `L` address bar, `F` find, `D`
bookmark, `Shift+A` agent panel, `,` settings, `J` or `Cmd+Opt+I` /
`Ctrl+Shift+I` developer tools, `F12` the Audit panel, `Esc` dismisses, declines or cancels (it never approves).

- **Developer tools**: per-tab Console (levels, filter, a JavaScript prompt),
  Network (requests as they start; no status or timing yet) and Engine (panics
  and dead script threads), with Copy all and Save log.
- **Panels** (agent, library, settings, developer tools, audit) are resized by
  dragging the splitter; double-click resets it; sizes are remembered.
- **Pages' own controls** (dropdowns, `alert`/`confirm`/`prompt`, the colour
  picker, the context menu) are drawn by Ferrite; the file picker is a card where
  you type the path. A page whose script thread dies shows a banner with Reload.
- **Consent**: a pre-run panel for what the dry run saw beyond the prediction
  (Approve/Reject each item), a question when the real run steps outside it
  (*Allow once*, *Allow for task*, *Don't allow*), and a hand-off when a page wants
  a password (you sign in, the agent never types it).

## Watching what the agent, the LLM and Laya do

Open **Audit** (toolbar shield, or `F12`). The **Model calls** view is a timeline of
every call: what the agent ran, every LLM request with its full prompt and
answer, every Laya request, and whether Laya's answer was used or sent back to
the LLM, each with how long it took. Click a row to see what was sent and what
came back. A one-line summary at the top answers "is Laya making it faster?"
from the timings it has seen. If Laya is slower than the LLM here it pauses
itself for a few steps and says so, and the server logs the device it runs on at
start-up (a CPU is not a fast lane). The same events are appended to
`<data dir>/logs/model-activity.jsonl` (prompts and page text included, so treat
it like the pages themselves; it never leaves your machine). The **Security log**
view is the hash-chained record of network requests.

## Evaluating the defense

```
just eval                 # the 938-case corpus through every defense mode -> target/eval-report/EVAL_REPORT.md
just guard-eval           # the runtime guard when the dry run could not have seen the attack -> GUARD_REPORT.md
just redteam-corpus-check # the 909 generated cases match the generator
```

`just eval` needs no network and no API key unless you export
`FERRITE_MODEL_SMALL`/`FERRITE_MODEL_MAIN` and a key, in which case the
fingerprint prediction makes live calls (unset them to reproduce the reported
numbers). The scripted agent in it complies with every injection, which is the
worst case. `just guard-eval` measures what the real run does when the dry run
could not have seen the attack (the live app's situation). The component
red-team suites are `cargo test -p ferrite-ipi --test red_team_sanitizer` and
`cargo test -p ferrite-core --test red_team_scope`. `docs/EVALUATION.md` §8 has the
numbers and, more usefully, the limits.

**With a real model** (`docs/EVALUATION.md` §9, every flag in `docs/COMMANDS.md`
§6): `just live-eval-plan --provider gemini --model <tag> --corpus agentdojo`
prices a selection and calls nothing; `just live-eval ... --batch-size 10
--max-calls 100 --pause-ms 4000` runs a batch, resumable from
`target/live-eval/results/`; `just live-eval --report` writes `REPORT.md` and
`report.csv`. The AgentDojo corpus is regenerated from a pinned checkout with
`just agentdojo-check <checkout>` (`python3 scripts/import_agentdojo.py`).

## Logins and cookies

The browser profile (cookies, HSTS, saved HTTP credentials, web storage) lives
in `<data dir>/profile` and survives restarts. It is written when the window
is closed normally; a crash, `kill` or macOS Cmd+Q may lose that run's new
cookies. Whether a particular site lets you sign in is a separate question:
Google in particular may refuse an embedded engine (`docs/TO-DO.md` T-267).
`FERRITE_USER_AGENT` overrides the user-agent string, and Settings has a browser
identity choice (default: Firefox-compatible; ADR-018).

## When something goes wrong

Launched without a terminal (Finder, a launcher), the app writes standard error to
`~/Library/Logs/Ferrite/ferrite.log` on macOS (`ferrite.previous.log` is the run
before) and `$XDG_STATE_HOME/ferrite/ferrite.log` (else
`~/.local/state/ferrite/ferrite.log`) on Linux; run from a terminal it prints
there instead. Windows writes no log file yet (`docs/TO-DO.md` T-298). The first
thing to read is the `[ferrite-render]` line, which says whether the GPU or the
CPU renderer is in use and why; `FERRITE_RENDERER=gpu|cpu|auto` overrides it.
`just collect-logs` zips the log, crash reports and system information (and, on
macOS, a stack sample if the app is frozen) onto your Desktop to send with a bug
report; `just crash-report` prints where the newest macOS crash happened. Quitting
ends the process within 3 seconds of the window closing. `docs/COMMANDS.md` §8 has
the rest.
