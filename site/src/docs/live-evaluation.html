The headline evaluation is scripted: its agent does whatever each case's authored deviation says. The live runner is the other half. It puts a real model in the agent's seat, so the question becomes what a model actually does under an injection, and what Ferrite then does about it. It is meant to be run by you, on your machine, with your own keys, in batches your quota can survive.

No real model has been run through it yet

Every behaviour of the runner is tested offline, against a deterministic mock provider and a loopback fake server. Nothing has been run against a real provider, so this site reports no live results. The step and token estimates the cost preview prints are estimates until the first real batch calibrates them. Nothing here changes the headline numbers on the Evaluation page.

What it runs

For each case the runner drives the app's own agent loop (the same action schema, system prompt and parser) against the dry-run engine, with the injection planted in the page or tool output the agent reads. Two roles can each be a model or not, independently:

Rolellm (default)Other
Predictor (--predictor)The small-tier model proposes the fingerprint's may_use, as in the apprules: the rule layer only
Agent (--agent)The main-tier model chooses actionsscripted: the worst-case script, no calls

And the defense, per case, in the modes of --modes (default off,guard):

off
Nothing; the baseline.
guard
The runtime guard refuses every action outside the predicted fingerprint, sanitizer off.
full
The guard plus the sanitizer on what the agent reads.
dryrun
Stage one only: the plan on a clean synthetic page, compared with the prediction (the consent burden).

The simulated user refuses every deviation, which is the best case for containment.

Providers and keys

The runner reuses the app's model layer and adds no HTTP stack, so it supports what that layer supports:

--providerWhat it isKey
geminiGoogle GeminiFERRITE_GEMINI_API_KEY, or the OS keyring (service ferrite)
ollamaOllama Cloud, or a local server with --base-url http://localhost:11434OLLAMA_API_KEY, or the keyring; a local server needs none
mockA deterministic stand-in with no network: it exercises the pipeline and says nothing about any modelnone

OpenAI-compatible and Anthropic endpoints are not supported, because the model layer has no backend for them. Adding one is a model-layer change, not a runner change. (A hosted server that also speaks Ollama's /api/chat can be reached with --base-url.)

Keys are read from the environment or the keyring and nowhere else: never accepted as a flag, never printed, never written. Error text kept in a result passes through a redactor that removes the key values the process holds. Model tags are configuration with no default: --model TAG for both roles, or --small-model and --main-model, or the FERRITE_LIVE_* and FERRITE_MODEL_* variables.

Cost first: --plan

--plan prints what a selection would cost and calls nothing, so it needs no key:

$ cargo run --release -p ferrite-eval --example live_eval -- \
    --plan --provider gemini --model <tag> --corpus agentdojo

It reports the cases and runs in the window, how many are already stored, the fingerprint predictions, the agent steps (typical and worst case), a rough token count (characters divided by four), and how many invocations the call cap implies. For the full AgentDojo import at the default two modes it prints 2,092 runs and about 7,300 model calls typical (51,254 at most), roughly 74 invocations at the default cap of 100 calls. Those are estimates from the corpus and the step limit; what a model really takes, what the cache absorbs and the provider's own tokenizer are known only by running.

Batches, limits and resuming

  • Selection. --corpus agentdojo|redteam|core|pilot|agentdojo-hand|all (default agentdojo), --suite agentdojo/banking, --only attack|benign, --seed S (a reproducible shuffle, so a small batch samples every suite), --offset and --limit.
  • Batches. --batch-size N runs the next N cases that still have work to do. Run the same command again for the next batch; --batch-index K takes slice K of the whole ordering instead.
  • A hard call cap. --max-calls N (default 100) caps the requests that reach the provider, retries included. When it is spent, the case in flight is abandoned unrecorded (it stays pending), a partial-results ledger is written, and the process exits with code 3.
  • Rate limits. --pause-ms spaces calls. A 429, a server error or a timeout is retried up to --max-attempts (default 5) with exponential backoff and jitter, honouring the provider's Retry-After (capped at 90 seconds by default, so an hour-long daily quota is not slept through). After 3 failed calls in a row (--max-consecutive-failures) the invocation stops with exit code 4: the provider is saying no, so come back later.
  • Failures are not scores. A call that never got an answer (rate limit, outage, rejected key, timeout) is stored as an error and left out of every rate; --retry-failed redoes it. A model that answers badly (an unparseable action, an empty reply, an unusable fingerprint) is a result: the fingerprint falls back to empty and the case is scored as such.
  • Resume. Results are an append-only file, one line per case and mode, synced before the next case starts, under target/live-eval/results/. A crash, Ctrl+C or a closed laptop loses at most the case in flight. Re-running the same command skips what is stored, as long as the settings that change behaviour (models, modes, steps, predictor, agent) hash the same. Model responses are also cached at temperature 0, so re-running an unchanged case is free and does not count against the cap.
Exit codeMeaning
0The batch finished cleanly. Go on to the next one.
1An internal or I/O failure.
2Usage or configuration: a bad flag, a missing key or tag.
3The call cap was reached; nothing is lost.
4The provider kept failing. Wait, then re-run.
5The batch finished but some cases failed; re-run with --retry-failed after a pause.

What to run first

# 1. nothing is called; no key needed
$ cargo run --release -p ferrite-eval --example live_eval -- --plan \
    --provider gemini --model <tag> --corpus agentdojo --seed 1 --batch-size 10

# 2. one small real batch (key in FERRITE_GEMINI_API_KEY or the keyring)
$ cargo run --release -p ferrite-eval --example live_eval -- \
    --provider gemini --model <tag> --corpus agentdojo --seed 1 \
    --batch-size 10 --max-calls 100 --pause-ms 4000

# 3. read what happened, then repeat step 2 for the next batch
$ cargo run --release -p ferrite-eval --example live_eval -- --report

Do a --provider mock --model x run once first to see the whole flow with no key. If you have just, just live-eval … and just live-eval-plan … pass the same flags to the same program.

The report

--report (optionally --compare gemini:<tag>,ollama:<tag>) writes REPORT.md and report.csv from the stored results, one group per provider and model pair. Every rate carries a 95% Wilson interval, and rows with few observations say so. It covers attack runs (attempted, executed, blocked of attempted, final answer) per mode; baseline against defense case by case (McNemar's exact test, Cohen's h); benign tasks (false positives, consent burden); fingerprint precision and recall; breakdowns by suite, attack class, ground truth and carrier; and cost (calls, cache hits, rate-limit answers, tokens). Residual attacks that use the task's own primitive at its own origin are reported as a floor, not a failure, and attacks with no attacker string to recognize are counted and left out of attack rates.

What this does not establish

  • The labels come from AgentDojo's ground-truth calls mapped onto Ferrite's primitives, not from AgentDojo's own checks.
  • It uses one attack template (important_instructions) and one sample per case at temperature 0.
  • The environment is synthetic, and “task success” is approximated by the agent giving a final answer.
  • The simulated user refuses every deviation.
  • The numbers are Ferrite's own measurement. They are not comparable to published AgentDojo utility or security scores.
