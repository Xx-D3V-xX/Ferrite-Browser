Two ways to a running browser: download a build, or build it yourself. This page is the second, plus how the downloadable builds are made. Every command below was read from the repository's justfile, scripts or workflows; where something has not been run, it says so.

Two builds

BuildWhat it is forCost
Without Servo (the default)The interface, the agent loop, the defense and the evaluation. It cannot render web pages: the engine stub refuses to start.About two minutes cold, and no network or API key for the test suite.
With Servo (--features ferrite-servo/servo)Real web rendering. This is what the downloadable builds are, in the release profile.The first build takes 20 to 60 minutes and 10 GB or more of disk. Later builds are incremental.

You need git, a Rust toolchain (the repository pins stable with rustfmt, clippy and llvm-tools), python3, and a C toolchain with cmake and pkg-config. On Linux the Servo build also needs the engine's own system libraries; the setup script points to the list but does not install them. just is the command surface (just --list prints every recipe); each recipe is a thin wrapper, so you can run the plain command instead.

Windows

The build, test, evaluation and probe recipes are plain cargo or python3 commands. The local helper recipes (setup*, run-local, run-fast, run-all, models-local, laya-*, doctor, collect-logs, crash-report) call bash scripts and have not been run on Windows. On Windows use the downloaded build, or cargo run --release -p ferrite-shell --features ferrite-servo/servo.

The shortest path to real pages

$ cargo run --release -p ferrite-shell --features ferrite-servo/servo

It opens the browser. No environment is needed: connect a model afterwards from Settings (Cmd/Ctrl+,). With just, the equivalent through the helper scripts is:

$ just setup-servo            # checks your toolchain, builds with Servo, writes .ferrite/env.local
$ just run-fast --no-model-check

First-time setup

RecipeWhat it does
just setupChecks the toolchain, builds ferrite-shell without Servo, optionally sets up the local Laya server, and creates .ferrite/env.local from scripts/local.env.example (never overwritten). Safe to re-run: each step checks first. With neither --with-servo nor --no-servo, an interactive run asks; a non-interactive one builds without Servo.
just setup-servoThe same, with the real engine. Ctrl-C is safe: re-running continues where cargo left off.
just setup-allServo and Laya together, all inside the repository folder.
just doctorA read-only checklist: tools, build, configuration, Laya and disk. It never prints a key. --fix-hints says how to fix each problem.

Flags pass through, for example just setup --dry-run --yes prints every action it would take and runs none. The scripts never use sudo: they offer to install rustup and Homebrew packages only after you say yes or pass --yes. All local state lives under $FERRITE_HOME, which the scripts default to the repository's gitignored .ferrite/, so rm -rf .ferrite removes it.

The helper recipes load $FERRITE_HOME/env.local (plain KEY=VALUE lines read as data, never executed; only FERRITE_*, OLLAMA_*, GEMINI_* and RUST_LOG are honoured, and anything already exported in your shell wins). They then check that FERRITE_MODEL_SMALL and FERRITE_MODEL_MAIN are set and exit with instructions if they are not. Pass --no-model-check to open the browser anyway and connect a model from Settings instead. Other flags: --no-laya, --servo or --no-servo, --wait SECONDS, --dry-run.

Model names are never defaulted, because providers retire them. just models-local lists the tags your Ollama endpoint serves (it needs a key, or a local Ollama).

A downloaded app does not read env.local

The packaged apps ignore env.local and any FERRITE_* variable you did not export before launching them. Connect a model from the Settings drawer. (The README.txt inside the Linux package still says to put your key in ~/.ferrite/env.local; that is out of date, the app never reads that file.)

The renderer: GPU or CPU

Pages are drawn by the engine into an off-screen buffer. Which context it uses is chosen once per run, and the choice is written to the log:

[ferrite-render] GPU rendering (<renderer name>)
[ferrite-render] the GPU path did not pass its self-test (<error>); using the CPU renderer
[ferrite-render] CPU rendering (FERRITE_RENDERER=gpu to try the GPU)
FERRITE_RENDERER=auto
The default. Tries the GPU on macOS only, where the CPU path is Apple's generic software OpenGL, the likely reason pages felt slow. On Linux and Windows it uses the CPU renderer.
gpu
Try the GPU on any platform. The context proves itself first by clearing to a colour and reading it back, and falls back to the CPU renderer on any failure.
cpu
Never use the GPU. hardware and software are accepted spellings of gpu and cpu.

Never run on a real GPU

The GPU path is pixel-identical to the CPU path on Mesa's software OpenGL, which is all it has been run on. It has not run on a real GPU or on a Mac, and no speed-up has been measured. The first thing to check on a new build is that [ferrite-render] line in the log. The same release also tells the engine the window's display scale (a Retina page was previously laid out twice as wide as it looks) and sizes the style, layout and worker thread pools to the core count; neither has been timed on real hardware.

Release builds

The downloadable builds come from two GitHub workflows, both started by hand:

  1. CI is manual only (Actions, Run workflow); there is no push, pull-request or schedule trigger. On Linux, Windows and macOS it runs format, lint (all targets, warnings denied), the full test suite and a Servo-free build, with unused-dependency, licence and doc-drift checks on Linux. Only if that passes everywhere does a second job build the release binary with Servo on each OS and package it.
  2. Release runs by itself when a manual CI run finishes, and publishes only if that run succeeded on every job. It replaces the rolling prerelease tagged latest, whose notes name the commit, branch and CI run. It never checks out or runs the CI run's code.

Checks before you change anything

RecipeWhat it does
just checkcargo fmt --all --check, cargo clippy --workspace --all-targets -- -D warnings and cargo machete (unused dependencies). It does not build Servo.
just testcargo test --workspace. It needs no network and no API key. If you are short on disk, test one crate at a time (cargo test -p ferrite-ui): linking the whole workspace is what runs out of space.
just auditcargo deny check: licences, advisories, duplicate versions. It needs the network for the advisory database.
just cicheck then test: the local equivalent of CI's lint and test job.

Looking at a page without the app

page_shot loads a URL in the real engine and prints what happened (title, load time, console messages, a count of requests by kind) and writes a PNG. It needs the Servo build.

$ cargo run -p ferrite-servo --features servo --example page_shot -- \
    https://example.com 8000 out.png 1280 800 1

The arguments are the URL, how long to run the engine in milliseconds, the output file, the frame size in device pixels and the display scale (2 renders as a Retina screen would, so a 1280-pixel frame is a 640 CSS-pixel viewport). The other probes (probe-input, probe-web-api, probe-engine, probe-controls, probe-profile) drive the same real engine headlessly against local pages; just --list names them. They are not part of CI.
