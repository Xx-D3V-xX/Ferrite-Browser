A security project that hides its weaknesses cannot be evaluated. This page gathers every known limit in one place: what the defense cannot stop, what the evaluation cannot show, and what the product cannot do yet. Where a limit is pinned by a test, the test stays in the repository, so the limit cannot quietly disappear.

Ferrite is a research prototype

Do not use it to protect anything you cannot afford to lose. The numbers in the documentation describe an architecture under a particular experiment, not a guarantee.

Limits of the defense

The residual: attacks inside the prediction

The architecture contains every attack that needs an action outside what the task implied, and nothing else. An attack that uses the same capability at the task's own site, or that is data-only (for example, tampering with the content a legitimate action returns), is indistinguishable from the task. In the evaluation this is 122 of 809 attacks (15.1%) with the sanitizer off. It is reported as a floor and kept in every denominator.

Open-ended scopes

Under a task_open scope every origin is admitted, so nothing distinguishes the attacker's destination. An open-ended prompt that matches no rule produces an empty fingerprint, which sends everything to consent. That is safe but noisy; a follow-up like “do the same for the second one” predicts a looser fingerprint because the dry run sees no page content, and may raise more prompts. The fail-safe direction is accepted.

The sanitizer

It is pattern matching over de-obfuscated views. It misses, by construction and pinned by tests: paraphrase, languages outside its list, syllable hyphenation, spelled-out markup or URLs, reversed non-Latin text, and payloads split across separate elements. It also has known false positives: pages that discuss attacks (“attackers exfiltrate data”, “never ignore the previous warnings”) and any mention of “system prompt”. The architecture does not depend on it.

The runtime guard

  • A click by CSS selector, a form action (submit, Enter in a field) and a server-side redirect cannot be resolved to a destination before they run. The tab's new origin is checked on the next action, after the request has been made.
  • A trailing-dot host (example.com.) fails closed.
  • Within-fingerprint abuse is indistinguishable from the task, by construction.

The human

The consent gate is a person. A user who approves everything defeats it: in the original run, approving every flagged action left 45.5% of attacks succeeding, against 0% when every flagged action is rejected. Real behavior is somewhere in between, and no human-factors study has measured where.

The model

Ferrite bounds what a compromised agent can do. It does not make a model less gullible. A model that is fooled will still try the action; the defense is that the attempt is contained, not that it is never made.

Limits of the evaluation

  • The agent is scripted. It re-enacts each case's authored deviation from ground truth, so the results say nothing about how often a real model takes the bait.
  • The fingerprint is rules-only by default. The 0% false-gate rate is for a well-behaved scripted agent under that prediction. A real agent's rate depends on what it does and on the model prediction layer, which the default run does not exercise.
  • Self-authored and generated. The corpus was written by the defense's author and expanded from shared templates, then tuned against. The intervals treat matrix-correlated cases as independent, so they understate the uncertainty.
  • No independent slice to speak of. Only three of the 938 cases are external (AgentDojo), which supports no claim. There is no second author, so Cohen's κ for annotation agreement is not computable and has not been faked.
  • The 1,046-case AgentDojo import has no results. It is checked in and validated offline, but it is the default corpus of the live runner, which has never been run against a real model. Its labels come from AgentDojo's ground-truth calls mapped onto Ferrite's primitives (some from the goal text alone), with one attack template and a synthetic environment, so even its future numbers will not be comparable to published AgentDojo scores.
  • No real model has been the agent. A live runner exists for Gemini and Ollama; no run has produced a result. OpenAI-compatible and Anthropic endpoints cannot be selected, because the model layer has no backend for them.
  • ADR = 100% is by construction. It measures the comparator against a scripted agent that issues exactly the declared deviation.
  • Missing quantities. Task-completion parity for benign tasks (no benign baseline under Off) and extra token cost (no token usage in the execution record) are not computed, for stated reasons.
  • A live-provider run is not reproducible byte for byte, so it is reported separately.

Limits of the product

Most of the newest work has only run on Linux

The DevTools panel, resizable panels, page-control overlays, crash banner, calmer approval cards, GPU renderer and display-scale fix were checked on Linux, rendered under a virtual display at normal pixel density, and, for the engine parts, run in the headless engine. None of it has run on a Mac, on a Retina screen or on a real GPU. The build on the releases page (commit f4ed744, 2026-10-02) predates most of it.

Websites that do not work yet

  • GitHub does not open in the owner's build, and the cause is unknown. The first log was empty. A script-thread panic was found and fixed in a vendored engine patch, but it was never reproduced, so it is not proven to be the cause. What would settle it is the log or the collect-logs zip from a build that has the new console and request logging, captured right after loading GitHub (see Debugging and logs).
  • The Google results page was pinned to the left edge. That is attributed to the engine never being told the display scale (a Retina page was laid out twice as wide as it looks), which is now fixed, but nobody has seen it directly, and Google could not be loaded where this was investigated. It needs a screenshot from a new build.
  • Google and GitHub sign-in may still be refused. These sites decide from the whole session, and Ferrite uses a young engine. The identity choice, the engine's added Web APIs and the sign-in handoff are what Ferrite does about it; none is a guarantee, and it has not been verified against those sites. Google sign-in in particular is still an open report. Still missing in the engine: service workers, navigator.mediaDevices (WebRTC), navigator.userAgentData and window.chrome. Ferrite deliberately does not fake any of them, nor hardware, canvas or renderer details, nor hide automation.
  • Web compatibility is Servo's. Ferrite renders with the Servo engine, and several CSS features current sites rely on are missing or broken in it: :has(), container queries, mask-image, backdrop-filter, text-wrap, subgrid, popovers, and aspect-ratio on block boxes (a box with a width collapses to zero height). Pages that depend on them will look wrong. Ferrite enables the engine features that were measured to work (adoptedStyleSheets, FontFace, WebGL, and a further seven Web APIs found by testing every default-off engine switch one at a time) and leaves off those that were measured not to, such as WebRTC (it would hand out the microphone with no prompt), geolocation and service workers, and injects one small script so that icons coloured by CSS stay visible (Servo paints them black otherwise), but it cannot add layout features the engine does not have.
  • Zooming and interaction fail on some pages, unexplained. The page crash banner and the Engine tab now surface script-thread panics, and dropdowns and dialogs now work, which were the two candidates. Whether they account for what was seen is not known.

The browser

  • The DevTools Network tab has no status, size or timing. A request is listed as it starts, with its method, type and URL; the engine's response callback is not wired up, so there is no status code, duration or waterfall. fetch() and XHR are listed as Other.
  • The file picker is a typed-path card. There is no native file dialog. The request reaches the browser and an answer path exists, but it has not been exercised against a real upload.
  • HTTP basic-auth prompts and input-method (IME) composition are not handled. A page behind basic auth gets no prompt, and composed text (Chinese, Japanese, Korean and similar input) is not forwarded. Non-US keyboard layouts, dead keys and key repeat have not been observed.
  • F12 opens the Audit panel, not DevTools. DevTools is Cmd+Opt+I or Ctrl+Shift+I, or Cmd/Ctrl+J. Whether F12 should change is an open decision.
  • Address-bar search is Google; the agent's search is not. Typing a query in the address bar goes to Google. The agent's own prompt still tells it to search with DuckDuckGo Lite and not to use google.com, because Google's pages stayed blank in this engine when that was written. Whether Google's results page now renders properly has not been confirmed.
  • Cookies are written on clean shutdown. Closing the window saves the profile; a crash, a kill or macOS Cmd+Q that bypasses the window close loses that run's new cookies. A 3-second quit watchdog ends the process after a window close, but whether it also covers Cmd+Q is unknown.
  • Linux keys do not persist across a restart with the kernel-keyring backend this build uses; see Models and settings.

Speed and the renderer

  • Speed on real hardware is unmeasured. Measured, in the headless engine on Linux: the fix that stopped the shell copying and re-uploading the whole page every tick. Not measured anywhere: the GPU rendering path, the thread pools sized to the core count, and the release profile as just run-fast builds it. An on-disk HTTP cache was tried and removed, because the engine's disk cache stores only entries evicted from memory and did nothing across restarts.
  • The GPU renderer has never run on a real GPU or on a Mac. It is pixel-identical to the CPU path on Mesa's software OpenGL, which is all it was tested on. It is chosen automatically on macOS only and falls back to the CPU renderer if its self-test fails; FERRITE_RENDERER=gpu|cpu|auto overrides it.

Logs and builds

  • No log file on Windows. Redirecting standard error to a file is Unix-only in the current code, so a Windows run prints to its terminal or nowhere. collect-logs is a bash script: macOS and Linux only, with the stack sample macOS only, and bundled in the macOS app only.
  • Unsigned builds. Each platform asks you to confirm the first launch, and on macOS the app is ad-hoc signed but not notarized.
  • Builds lag the source. Builds are made by a manual CI run, and the release page names the commit it came from.
  • The macOS app has crashed for the owner. It was reported to crash repeatedly, to need a force-quit, and to fail on some pages. A log file, a quit watchdog, crash reporting and the DevTools Engine tab were added to make that diagnosable, and none of them has been run on that Mac yet. How the packaged Windows and Linux builds behave on real machines has not been checked by the project.
  • A build without Servo cannot render pages. It is for the interface, the defense and the evaluation.
  • No LICENSE file yet. The crate manifests declare MIT OR Apache-2.0, carried over from an earlier file's stated intent, and the choice has not been confirmed by the project owner.

What is explicitly not claimed

  • That Ferrite makes AI browsing safe, or safe in production.
  • That any model is robust to prompt injection because it sits behind Ferrite.
  • That the evaluation generalizes to attacks, tasks or sites outside the corpus.
  • That users will reject unexpected actions; the headline numbers assume they do.
  • That the defense survives an attacker who has read it. The corpus was tuned against, and no held-out, adversarial, independently authored evaluation has been run.
  • That the sanitizer detects injected text in general. It detects the patterns it has.

What would make the claims stronger

  • An independently authored, held-out corpus, run once, with a defense brief withheld from the authors.
  • A run with real models as the agent, reporting how often they take the bait and what the defense contains.
  • A human-factors study of how people actually answer consent prompts.
  • The model prediction layer measured on its own, with the sanitizer and rules off.

If you can do any of these, or find an attack that gets through, open an issue. A bypass is a result, and the corpus is where it belongs.
