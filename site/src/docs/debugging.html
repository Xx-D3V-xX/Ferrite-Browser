A page that looks wrong, a site that will not open, an app that froze: this page is how to find out what the page or the engine said about it, and what to send when you ask for help. Ferrite keeps a console and a request log per tab, a log file for runs without a terminal, and a script that gathers everything into one zip.

Which build has this

The log file is in the build published on 2026-10-02 (commit f4ed744). DevTools, the crash banner and the log-collection script are newer and are not in it yet; build from source to use them (Run it from source). Screenshots here were rendered on Linux.

DevTools

Open the panel with Cmd+Opt+I on macOS or Ctrl+Shift+I elsewhere, with Cmd/Ctrl+J, or from the menu (Developer tools). It is a bottom drawer with three tabs; counts show on the tab labels. Drag its top edge to resize it.

F12 does not open DevTools. It opens the Audit panel (the model-call timeline and the hash-chained security log), so a habit from Chrome will show you something else. Whether F12 should open DevTools is an open decision.

Console

  • Every message the active tab's page printed, at every level (log, info, warn, error, debug), plus uncaught exceptions, which carry the file, line and column. Each tab has its own log.
  • A filter box, level chips with counts (All, Errors, Warnings, Info, Debug) and a Preserve log checkbox. Without it, a navigation starts the log afresh; with it, the log is kept and the navigation is marked.
  • Identical consecutive messages fold into one row with a count; long messages fold to a few lines with Show more.
  • A prompt, Run JavaScript on this page: type an expression and press Enter or Run; ↑ and ↓ recall earlier input (the last 100). This is you running script in the page, not the agent.
  • Bounds: at most 5,000 rows per tab, 4,000 characters per message and 8 MiB of message text per tab; the oldest rows go first.

Network

Each request the tab made, as it starts: relative time, method, type and URL, with a filter box and type chips (Doc, JS, CSS, Img, Font, Media, Other). fetch() and XHR requests fall under Other.

What the Network tab cannot tell you

There is no status code, size or duration, and so no waterfall: the engine's response callback is not wired up yet, and the panel says so. A request that fails or returns 404 is listed like any other. For a failed load, look in the Console, which is where the page reports it.

Engine

Panics on engine threads and pages whose script thread died, this session, each with the thread, message and location, and a backtrace you can show or hide. The engine's own threads panic quietly: without this tab the symptom is a page that simply stops answering.

Header buttons

Copy all
Copies everything in the current tab to the clipboard as text.
Save log…
Writes the current tab to ferrite-<console|network|engine>-tab<N>-<date-time>.log in the log folder (below).
Open log folder
Opens that folder in Finder, Explorer or your file manager.

Warnings and errors from the console are also written to the log file, as lines like [console:error] tab 1: …, at most 20 per tick of the interface so one noisy page cannot flood it.

The log file

A browser launched from Finder, a Start menu or a launcher has no terminal, so its standard error would go nowhere. Ferrite points it at a file instead. Launched from a terminal, it prints to the terminal and writes no file.

OSFolderFiles
macOS~/Library/Logs/Ferrite/ (Console.app shows it under Log Reports)ferrite.log, and the previous run as ferrite.previous.log
Linux$XDG_STATE_HOME/ferrite/, otherwise ~/.local/state/ferrite/the same two names
Windows%LOCALAPPDATA%\Ferrite\logs is where DevTools saves logsNo ferrite.log is written on Windows: redirecting standard error to a file is Unix-only in the current code. Run it from a terminal to see the output.

The file starts with a banner naming the version, OS, architecture and process id. Panics always carry a backtrace (RUST_BACKTRACE=1 is set for you when you have not set it). If the interface stops ticking for 8 seconds, one line says so (the UI has not responded for …), and one more when it recovers. When you close the window, the process ends within 3 seconds whatever the engine is doing, and says so in the log if it had to. Whether that watchdog also covers Cmd+Q on macOS, which goes through the system menu, is not known.

The first line to look for on a new machine is the renderer line (see the renderer): it says whether the GPU or the CPU is drawing pages, and why.

Collecting logs to send

$ bash scripts/collect-logs.sh                                      # from a checkout
$ bash /Applications/Ferrite.app/Contents/Resources/collect-logs.sh  # from the macOS app

(or just collect-logs in a checkout.) It writes one zip, ferrite-logs-<date-time>.zip, to your Desktop (your home folder if there is none), and prints its path. It contains:

  • ferrite.log and ferrite.previous.log, or a NO-LOG.txt saying there is none;
  • on macOS, the three newest Ferrite crash reports from ~/Library/Logs/DiagnosticReports;
  • on macOS, if Ferrite is running right now, a 5-second stack sample of it: run the script while the app is frozen;
  • system.txt: on macOS the OS version, hardware and display listing; elsewhere uname and the CPU.

Nothing is uploaded, but the log can contain page URLs and console errors, so read it before you send it. The script needs bash and zip; it does not support Windows, and the sampling part is macOS only. The bundled copy is in the macOS app only. After a crash on macOS (exit code 139), just crash-report prints the exception and the crashing thread's stack from the newest report, with only Python's standard library.

Reporting a page that does not work

Useful, in order of usefulness: the address; the Console and Engine tabs (Copy all); whether the page shows the crash banner; the [ferrite-render] line and the first lines of the log; and the zip above. page_shot (see Run it from source) reproduces a page load without the app.
