Ferrite's guarantee is not “this text is safe”. It is “this action was inside what your task needed, or you approved it”. This page walks through how that is decided, stage by stage, and which invariants hold it together.

The capability model

A capability is not an invented domain tool such as “email.read”. It is an action class, a group of primitives that share a security character, paired with an origin scope, the places it may act. “Email” is a property of the scope, authored per task, never a tool the model can conjure.

CapabilityAllows
web.readReading page content.
web.navigateNavigating to a page.
web.interactClicking, typing, filling and submitting.
web.downloadDownloading files.
scoped.readCookies and web storage, only when named.
clipboard.read, clipboard.writeClipboard access.

The vocabulary is closed: there are exactly seven capabilities, and a model's output is filtered against that list. A scope is one of three typed kinds, ordered from tightest to loosest:

exact
Specific known origins. The tightest scope.
domain_suffix
A bounded family, such as *.wikipedia.org.
task_open
Genuinely open browsing. Requires a written rationale and is reported as a weak scope, because under it every origin parses as admitted.

Each capability carries its own scope, so a task can combine a narrow cookie read on one site with a wide page read for search results without either widening the other. Origins are compared after normalization, whole-host, never by prefix: localhost.evil.example is not local.

Invariant: js.execute is unconditionally unscopable

Running arbitrary JavaScript can synthesize any other primitive past the tool boundary, so no capability's expected realization may include it, at any scope. It is always a deviation and always consent-gated. This is enforced in the type system: there is no capability variant that could authorize it, so a prediction cannot even express it.

1 · Predict

Before any page is fetched or any tool runs, Ferrite turns your request alone into an expected fingerprint with two layers:

  • The rule layer (must_use) is deterministic, offline and pure. It matches whole words in your request: “open” or “go to” imply navigation; “summarize”, “list”, “search” and other everyday read verbs imply a page read; “download” implies a download; “fill”, “submit” or “send email” imply interaction; and cookies or storage are granted only when you mention them. It does not match substrings, so “information” does not grant form filling. An open-ended prompt that matches nothing yields an empty fingerprint, which routes everything through consent.
  • The model layer (may_use) asks the configured fast model what the task might plausibly need beyond the rules. The answer is untrusted text: each label must be exactly one of the seven capability names or it is dropped at the boundary.

Fail to empty, never to a bypass. A provider error, timeout, rate limit, malformed or empty body, or a missing key degrades the model layer to the empty set. It never skips fingerprinting and never widens what is admitted. An empty prediction routes everything through consent. The cost of an outage is more prompts, not less safety.

2 · Sanitize

Before content reaches the agent, a sanitizer looks for instruction-like text and cuts it out. It is a risk reducer, not the foundation: the architecture still holds with it switched off, which is how the evaluation measures the two separately.

  • Matching on meaning, not spelling. Text is matched in de-obfuscated views: zero-width characters removed, look-alike and full-width letters folded, escapes (HTML, URL, \u) decoded, leetspeak, ROT13, reversed text, base64 and hex, and invisible Unicode tag characters. Each byte maps back to the original span, so detection reports the original snippet and excision cuts the original sentence.
  • Pattern set v2 covers instruction override, agent-addressing, concealment, exfiltration, chat-template and action-mimicry patterns, markdown-image exfiltration and prompt extraction, in eight languages, plus a hidden-Unicode check.
  • Everywhere a digest shows text. Attribute values (alt, title, placeholder, aria-label, href), CSS-generated text and the raw page text are scanned, not only the visible body.
  • Linear time. Excision is linear in input size; a 1 MB page with no sentence terminators is handled without a hang.

It is still pattern matching. Paraphrase, languages outside the list, spelled-out markup, reversed non-Latin text and payloads split across elements are missed by construction, and the test suite pins them as known misses so the inventory stays honest.

3 · Dry-run

The agent's plan is executed against a synthetic twin: plausible fake data, served by a stand-in engine that records every call and performs no real I/O. Containment here is by construction, not by an interceptor that could be bypassed: the dry-run engine simply has no real network to reach.

  • Twin data is encrypted at rest with a key from the OS keyring or an environment variable, never a constant compiled into the binary.
  • A download or a new tab is recorded at its destination origin and as a network attempt. Recording it at the page's own origin would let an agent on an allowed site fetch from an attacker without producing a deviating event.
  • A whole-turn timeout returns the partial record instead of discarding it.

4 · Compare

The comparator takes the expected fingerprint and the dry-run record and produces a diff: extra primitives (capabilities the task did not imply) and out-of-scope origins (places the task did not authorize). Every event is classified by one function, classify_event, which the comparator and the runtime guard share, so they cannot disagree; a sweep test covers every primitive, origin and fingerprint combination.

5 · Consent

If the diff is non-empty, nothing real runs. The consent panel lists each deviation in plain language and asks per item: approve or reject. It is drawn by the application, outside page content, and only the items you approve are added to what the real run may do. The plain-language lines name the offending action and the origin your request actually authorized, so a lookalike domain is visible as such.

The runtime guard

The dry run executes against synthetic pages, so a page that carries an injected instruction exists only in the real run, where the dry run cannot see it. If the loop compared once and then ran every real action, a deviation that only a real page provoked would be compared against nothing. The guard closes that gap.

  • Every real action is classified and does not run unless it is in expected ∪ approved: what the predicted capabilities and their scopes admit, plus what you approved in this task's consent prompt.
  • The effect of an action is what is checked: a URL action at that URL's origin, anything else at the active tab's origin, and a click by @ref on a link whose href leads elsewhere counts as a navigation there.
  • A block tells the agent a fixed sentence containing nothing from the action or the page, because an observation goes back to the model and anything attacker-chosen echoed there is itself an injection channel.
  • The block is shown to you, committed to the audit log (CapabilityDenied), and the fourth block ends the run.
  • An empty prediction blocks everything it was not given consent for.

Its stated limits: a click by CSS selector, a form action (submit, Enter in a field) and a server-side redirect cannot be resolved to a destination before they run, so the tab's new origin is checked on the next action, after the request was made. See Limits.

The audit log

Security-relevant events are appended to a SQLite-backed log in which every entry commits to the one before it:

  • Hash chain. Each entry's hash covers its content and the previous entry's hash, with a fixed domain-separation prefix and a schema version, so reordering or editing an entry breaks every hash after it.
  • Full coverage. Every persisted column is in the hash preimage. An earlier version omitted two columns, so they could be rewritten while verification still passed; that was fixed and is covered by a tamper test matrix.
  • Canonical form. The preimage is serialized as JSON in a fixed field order, not Debug output, so null and the empty string are distinguishable and every string is length-delimited.
  • Verifiable. verify_chain() recomputes the chain; the evaluation records one entry per execution (96 in the original run) and checks it.

Two logs, on purpose

The model-activity trace (every prompt, answer and timing) is kept separately from the audit log. The audit log is small, hash-chained and about decisions; the trace is bulky and local, and mixing them would make the log neither small nor tamper-evident in a useful way.

Invariants at a glance

  • The fingerprint is built only from text you wrote. Page text, agent output and steps never feed it.
  • A model's labels are filtered through a closed list; anything else is dropped.
  • Any provider failure empties the prediction. It never bypasses it.
  • js.execute can never be expected, at any scope.
  • The comparator and the guard classify identically, by sharing one function.
  • The agent never types into a password, one-time-code or card field: the page script refuses, and a page that needs one pauses the run for you (the sign-in handoff).
  • No test needs the network or an API key; live-provider tests are opt-in.
