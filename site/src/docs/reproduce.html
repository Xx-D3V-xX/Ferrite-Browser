The evaluation is meant to be re-run, not taken on trust. The default path needs no network, no API key and no GPU, and it is deterministic: the same corpus in produces the same numbers out, apart from wall-clock timing fields.

What you need

  • A recent Rust toolchain. Optionally just; every recipe below is a one-line cargo or python3 command you can run directly.
  • The repository: git clone https://github.com/rayanjainn/Ferrite-Browser.
  • Nothing else. The evaluation crate is Servo-free, so none of this builds the browser engine.

Run the evaluation

$ just eval
# or:
$ cargo run -p ferrite-eval --example eval

This runs every case under all four modes (the 938-case corpus, 3,488 executions), appends one entry per execution to a hash-chained audit log, verifies the chain, and writes the report to target/eval-report/ (or $FERRITE_EVAL_OUT_DIR):

EVAL_REPORT.md
The metrics tables: per-mode, per-tier, mode-pair tests with Holm correction and effect sizes, the consent-policy sweep.
eval_report.csv
One row per execution, for your own analysis.
audit.db
The audit log the run produced; its chain is verified as part of the run.
corpus.db
The SQLite store of the cases and their execution records.

Unset your model variables first

The reproducible numbers come from the rules-only fingerprint with no model. If FERRITE_MODEL_SMALL, FERRITE_MODEL_MAIN and a provider key are set in your environment, the fingerprint's prediction layer makes live calls instead and the run is no longer reproducible. The scripted agent never calls a model either way.

Run the runtime-guard experiment

$ just guard-eval
# or:
$ cargo run -p ferrite-eval --example guard_eval

Runs the compromised real run against a dry run that cannot see the attack, with each action checked by the guard. It writes target/eval-report/GUARD_REPORT.md: attacks that succeed without and with the guard, per stratum, and the benign tasks it blocked.

Run the test suite

$ just test
# or:
$ cargo test --workspace

This includes the component red-team suites (sanitizer, scopes, rule layer, guard, dry run, audit-log tamper matrix) and the corpus validation. It needs no network and no key; a test that would touch a live provider is marked #[ignore] and runs only on request (just test-live).

Inspect a single case

$ cargo run -p ferrite-eval --example inspect_case -- \
    crates/ferrite-eval/tests/corpus/c11_offscreen_scope_escalation.json

Runs one case file under every mode it defines and prints each layer's caught or missed verdict, the final outcome, and whether that matches what the case's authored ground truth implies. It is the quickest way to see why a particular attack was or was not contained.

Regenerate the corpus

$ python3 scripts/gen_redteam_corpus.py            # or: just redteam-corpus
$ python3 scripts/gen_redteam_corpus.py --check    # or: just redteam-corpus-check

Writes the 909 generated cases to crates/ferrite-eval/tests/corpus_redteam/ from the matrix described in Evaluation. Labels come from the capability lowering table, not from running the defense. corpus_redteam_validate checks the table and every task's capability set against the real code. --check fails if the files on disk differ from a fresh generation; on the current tree it reports that all 909 files match.

Check the AgentDojo import

The 1,046-case AgentDojo corpus (see Evaluation) is checked in. Its structure is verified offline by cargo test -p ferrite-eval --test agentdojo_full_validate. Verifying that it matches AgentDojo needs the dataset, which is not in this repository:

$ git clone https://github.com/ethz-spylab/agentdojo /tmp/agentdojo
$ git -C /tmp/agentdojo checkout 089ed468cf3ed0322acc66b0211f26d9d90dbf60
$ python3 scripts/import_agentdojo.py --src /tmp/agentdojo --check

It parses AgentDojo's task files and never runs any of its code. Without --check it rewrites the corpus; an importer run against another commit refuses unless you pass --allow-other-commit, and the output must not be committed.

Try a defense mode in the app

The defense mode is read once at startup from FERRITE_DEFENSE: on (the default), off, sanitizer_only or loop_only. These are the same four conditions the evaluation compares, so you can reproduce the contrast on a page you control.

The optional live-provider runs

There are two ways to involve a real model. Neither is reproducible byte for byte, because a live model's answer is not pinned the way a scripted corpus is, and neither is ever blended into the headline numbers.

The fingerprint's prediction layer, in the same evaluation:

$ FERRITE_MODEL_SMALL=<a tag your account serves> \
  FERRITE_MODEL_MAIN=<a tag your account serves> \
  OLLAMA_API_KEY=<your key> \
  cargo run -p ferrite-eval --example eval

just models lists the tags your key can reach.

A real model as the agent is a separate runner, with batches, a cost preview and resume: see Live evaluation. It has not been run against a real provider yet.

What “reproduced” should mean

Reproducing the default run confirms the computation: that the stated corpus, run through the stated code, yields the stated numbers. It does not confirm that the corpus is representative of real attacks. For that, the right next step is a held-out corpus written by someone who has not read the defense.
