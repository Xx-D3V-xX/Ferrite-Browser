A defense is only as meaningful as the attacker it assumes. This page states that attacker precisely, what is trusted, and what is out of scope, so the evaluation can be read against it.

The attack

Indirect prompt injection is an attack on an agent through content it reads, as opposed to the user's own prompt. The attacker never talks to the agent directly. They plant text where the agent will look, and the agent, unable to reliably tell data from instructions, may follow it.

In a browser the consequences are concrete: navigating to an attacker's site, submitting a form, downloading a file, reading cookies or clipboard contents, or running script. Each of those is an action, and actions are what Ferrite checks.

The attacker

Can

  • Control the content of pages the agent reads, including hidden or off-screen elements, HTML comments, alt, title and meta text, CSS-generated text and visible text.
  • Control the content of tool results the agent receives, for example fields of a JSON response, free-text blobs, error messages and metadata.
  • Pick any wording: paraphrase, other languages, encodings, invisible characters, social engineering, or text split across elements.
  • Make several requests: a delayed payload or a redirect chain that only appears on a second read.

Cannot

  • Edit the user's prompt, or speak in the browser's own interface. The consent panel is drawn by the application, not by page content.
  • Modify Ferrite, the operating system, the model provider or the model weights.
  • Reach the user's real session during a dry run: it executes against synthetic data with no real network reachable.

The vocabulary the evaluation uses

The evaluation describes every attack along closed axes, so two authors tag a case identically.

Carrier vector
Where the payload rides. Web content: hidden element, off-screen text, HTML comment, alt text, meta content, CSS pseudo-element, visible text. Tool output: JSON field, text blob, error message, metadata.
Rhetorical technique
What the text argues: instruction override, context manipulation, social engineering, goal hijack.
Concealment
How it is hidden: plain, obfuscation, payload splitting.
Ground truth
Deviation (a capability or origin the task did not authorize), within-fingerprint origin shift, within-fingerprint data-only (the irreducible residual), or none (benign).

Out of scope, stated plainly

Ferrite does not claim to stop these

  • Attacks inside the prediction. The same capability, at the task's own site, with data-only abuse, looks identical to the task. This is the residual, reported as a floor and never dropped from the denominator.
  • A model that takes the bait. Ferrite bounds what a compromised agent can do. It does not make the model more robust, and the evaluation says nothing about how often a real model is fooled.
  • A user who approves everything. The consent gate is a human decision. With every flagged action approved, containment is much weaker; see the consent-policy sweep in Evaluation.
  • Open-ended tasks. Under a task_open scope every origin is admitted, so nothing distinguishes the attacker's destination.
  • A compromised machine, provider or build. Those sit below the trust boundary this design assumes.
