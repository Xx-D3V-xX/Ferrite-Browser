Ferrite does not ship a model. You connect your own, in Settings, and the app keeps the secret part (your key) and the non-secret part (your choices) in different places on purpose.

The “local” choice must be on this computer. This is deliberate: a bearer token must never be sent toward anything that is not the cloud service, and matching is on the whole host, so localhost.evil.example is not local. To use a remote Ollama server anyway, choose Ollama Cloud and set FERRITE_OLLAMA_BASE_URL to it; your key is then sent to that server, so only do this for one you trust.

The two models

Fast model
Runs once per task to predict which capabilities the task might need. It sees only your request. A small, quick model is fine.
Agent model
Reads pages and picks each step. This is where a stronger model pays off.

By default one model serves both roles. Names are not hard-coded anywhere: the list comes from your provider, because providers retire model names, and an unset name is a clear “choose a model”, never a stale default.

The key is held more carefully than the rest

  • The settings file contains no key, and a test fails if it ever does.
  • The key field is masked, and the field is cleared the moment the key is stored.
  • The message that carries a typed key prints <redacted>, and the key type prints Token(<redacted>), so a stray debug line cannot leak it.
  • Gemini puts its key in the request URL, so every error message from that backend is redacted before it is shown.
  • Remove key deletes it from the credential store and disconnects the running app, which would otherwise keep using the copy in memory.

Linux: keys do not survive a restart

This build stores keys through the Linux kernel keyring, which is held in memory and cleared when the computer restarts (macOS Keychain and Windows Credential Manager persist normally). On Linux, save the key in Settings to use it in the current session, and export it as an environment variable for a permanent one:

export OLLAMA_API_KEY=<your key>
# or
export FERRITE_GEMINI_API_KEY=<your key>

Using a persistent Secret Service backend instead is tracked as an open item.

How Settings and environment variables combine

What leaves your machine

  • Page content, to your model provider. The agent has to read pages to act, so the text it reads is sent to the provider you chose. With local Ollama, nothing leaves your computer.
  • Your request, to the fast model, to predict the fingerprint. Only text you wrote, never page text.
  • The model list request when you press Load models: your key (or none, for local) to the provider you chose, nothing else.
  • Nothing to Ferrite. There is no Ferrite server, and the source contains no analytics or telemetry code. Apart from what you ask it to do, the app makes one kind of request on its own: it fetches each site's favicon.ico, for the six quick-access tiles on the new-tab page and for the tabs you open.

The model-activity trace stays on disk locally and can contain prompts and page text. Treat the data directory accordingly.

Failing safely

No model, a bad key, a timeout or a malformed answer never relaxes the defense. The fingerprint's prediction layer fails to empty, which sends more actions to consent, and the agent loop fails closed rather than act without a model. Saving a configuration that cannot be built is refused with the reason, and the previous working connection is left untouched.

Laya: an optional fast lane

If FERRITE_LAYA_URL is set, an optional, separate server can pick routine browsing steps with a confidence gate, which saves model calls. It is never part of the security boundary: every step it chooses still passes through the same guard and consent as any other. The app logs, once, whether it is on and, if the server is not on this machine, that page text, URLs and element labels leave it. A governor pauses the lane automatically when it stops paying for itself. With the variable unset, none of this exists.
